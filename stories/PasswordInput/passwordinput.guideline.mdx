# Password Input

Use `PasswordInput` wherever a user types a password, rather than an `Input` of type
`password`. It is a field, not a labelled row: wrap it in a `FormGroup` as you would
any other field, so it works the same in a two-column form, in a modal, and in a
layout nobody has designed yet.

Use `PasswordFields` when the user is **setting** a password rather than typing one
they already have. It renders the password and its confirmation as two `FormGroup`s
and registers both fields itself, so it needs a `FormProvider` ancestor.

## `autoComplete` is required, and the value matters

There is no default, because both values look right on screen and only one of them
behaves. `current-password` asks the browser to fill in a password the user already
has; `new-password` asks it to offer a generated one and to save what is typed. A
field that announces `new-password` while asking for the current password gets
offered for saving instead of filled in.

## Setting a password

One reveal toggle drives both fields. The copy affordance is opt-in through
`copyable` and belongs on the first field only.

`PasswordFields` does not enforce that the two values match. A form with a
`resolver` ignores field-level validation, so that rule belongs in the caller's
schema; `confirmationRules` is there for forms that have no resolver.

A password form also needs a `username` field for password managers to offer the
right credential. It belongs to the application — the only side that knows the
username — so render it yourself, visible or hidden off-screen.

## Narrow containers

The field is always shrinkable: it stops at the narrowest width an `Input` can be
given, after which the row overflows rather than letting the field collapse. The
reveal and copy buttons keep their width throughout, so the field is the only thing
that gives.
