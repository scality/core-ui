# Table

A table displays structured data in rows and columns, allowing users to scan, sort, and act on multiple items.

## Column alignment

A column states its alignment once, in `cellStyle.textAlign`, and it reaches the header label and
every value in the column alike. Text reads left, a number reads right, a status or other short
enum reads centred. Header and values sit on the same edge whichever edge that is — a column whose
label and values disagree reads as two columns.

Sorting does not change that. A sortable header's caret reserves its own width rather than taking
it from the label, so an end-aligned label keeps the trailing edge; a centred label is balanced
against the caret rather than pushed off centre by it. On a column too narrow to hold both, the
centred label drifts off centre instead of truncating earlier than it would without a caret —
losing the middle of a label costs more than losing its exact centring.

## Hidden values

No value is hidden.<br />
When a cell cannot show all of its content, the rest is reached through a visible trigger.<br />
That trigger is a question mark placed next to the content, and it reveals the rest on hover.

A list of values that can be enumerated is a particular case: show the first value, then the
number of remaining ones as "+1" or "+2", then the question mark listing them all.

`IconHelp` provides the question mark. There is no component for the count, compose it from a
`ConstrainedText` for the first value and the count as plain text. Values hidden by a `dropAt`
breakpoint are a separate case, handled by `revealDroppedColumns` below.

## Action column

Tables may include an action column on the far right for row-level actions.

- `Header` must be an empty string. Never "Actions", "Details", or any other label.
- Buttons are right-aligned within the cell.
- Prefer `size="inline"` buttons.

## Loading and empty states

A table never tells the user a resource is empty before it has finished loading.

- While loading, the table keeps its header and shows the loading placeholder in place of the rows. Nothing moves when the rows arrive.
- "No results" is an answer, not a waiting screen. It appears only once loading has completed and there is genuinely nothing to show.
- When the data cannot be loaded, the table says so. It never falls back to "no results", which would tell the user the resource is empty when it is unknown.

`status` is required: `'idle' | 'loading' | 'success' | 'error'`. The table cannot tell "still loading"
from "loaded and empty" by looking at `data` alone, so it never guesses.

### What each status shows

| `status`    | Below the header, the table shows                                       |
| ----------- | ----------------------------------------------------------------------- |
| `'idle'`    | An empty body: no loader, no message                                    |
| `'loading'` | The loader, "Loading data..." or "Loading users..." with `entityName`   |
| `'error'`   | The error message                                                       |
| `'success'` | The rows, or "No results" when `data` is empty or a filter matches none |

Every status but `'success'` replaces the rows, including rows already on screen. A table that
receives `'loading'` on every refresh goes blank for the length of each request, so map your state
so that only the first load is `'loading'`, as below.

`'idle'` means nothing was requested: a disabled query, or one waiting for an input the user has
not given yet. Nothing is on its way, so there is no loader — it would spin forever — and nothing
has answered, so there is no "No results". If the user has to act before rows can load, such as
picking a node, say so next to the table.

Empty `data` with `status="success"` is the only way to show "No results". Any other `status` is a
type error. If a caller works around the type, the table warns in the console once for each value
it receives, and shows the error state when there is no data. Rows still render when data is
present, and "No results" shows if the filter matches nothing. The table never guesses loading or
empty.

### Mapping a query onto `status`

For react-query v3 and TanStack Query v5, pass the query result to `getTableStatus`:

```tsx
import { Table, getTableStatus } from '@scality/core-ui/dist/next';

const usersQuery = useQuery({ queryKey: ['users'], queryFn: fetchUsers });

<Table
  status={getTableStatus(usersQuery)}
  data={usersQuery.data ?? []}
  columns={columns}
>
```

v3 statuses pass through unchanged. v5 has no `'loading'` or `'idle'`: it reports `'pending'` until
the first response, which `getTableStatus` turns into `'loading'` while a request runs and into
`'idle'` when the query is disabled (`fetchStatus === 'idle'`). Both versions keep `'success'`
during a background refetch, so a polled table keeps its rows.

A dependent query is `'idle'` while the query it depends on loads. Pass `'loading'` for that wait,
or the table shows an empty body before the loader:

```tsx
status={nodeQuery.isLoading ? 'loading' : getTableStatus(volumesQuery)}
```

A redux or saga store usually raises one `isLoading` flag for every request and keeps the previous
rows meanwhile. Show the loader only while there is nothing to show:

```tsx
import type { TableStatus } from '@scality/core-ui/dist/next';

const status: TableStatus = error
  ? 'error'
  : isLoading && data.length === 0
    ? 'loading'
    : 'success';
```

`data.length === 0` stands in for "never loaded", and it is wrong in two cases. A store that starts
with `isLoading: false` reads as loaded and empty before its first request, so "No results" flashes.
A resource that really is empty shows the loader again on every refresh. If either shows, keep a
"loaded once" flag in the store and test it instead of `data.length`.

### Paginated tables

A table that grows page by page through `onBottom` takes the status of its **first page**. Once the
first page is in, the table is `'success'` and later pages append rows. A status covering every
page would keep the loader up until the last one arrives.

- `useInfiniteQuery` already works this way: `status` stays `'success'` while a next page loads, so
  `getTableStatus(query)` is the first-page status.
- A hook that fetches every page itself exposes the overall status and, beside it, the first page's.
  zenko-ui's `useAwsPaginatedEntities` returns `status`, which turns `'success'` after the last page,
  and `firstPageStatus`, which turns `'success'` after the first. Pass `firstPageStatus` to the
  table, and keep `status` for what needs every page, such as a total count.

### When a refetch fails

When a refetch fails while rows are on screen, react-query (v3 and v5) sets `status` to `'error'`
once its retries run out, and keeps the previous `data`. The table follows `status`: the error
message replaces the cached rows, and they come back on the next successful fetch. On a polled
table, one failed poll blanks it until the next one succeeds.

If the cached rows are still worth showing, keep `'success'` while there are rows and report the
failure next to the table, for example in a banner:

```tsx
const status =
  usersQuery.isError && usersQuery.data?.length
    ? 'success'
    : getTableStatus(usersQuery);
```

The redux mapping above makes the same choice in its first check: `error` replaces the rows,
`error && data.length === 0` keeps them.

### Migrating to a required `status`

Up to 0.233.x, `status` was optional and a missing one meant `'success'`. It is required since
0.234.0.

- Do not hard-code `status="success"` on a table whose data is fetched. During the first load it
  shows "No results", the message this prop exists to prevent. Hard-code it only for data that is
  never fetched, such as rows built in the page.
- For react-query or TanStack Query, pass `getTableStatus(query)`. Passing a TanStack
  `query.status` as is is a type error, because `'pending'` is not a table status; if the type is
  bypassed, every first load shows the error state.
- For a redux or saga store, use the first-load mapping above rather than
  `isLoading ? 'loading' : ...`, which blanks the rows on every refresh.
- `'idle'` used to show the loader, like `'loading'`. It now shows an empty body, so a table that
  passes `'idle'` while a request is in flight should pass `'loading'` instead.

## Row selection

Pass `onRowSelected` to `Table.SingleSelectableContent` to make rows selectable, and pair it with
`selectedId` so the chosen row stays marked. A selectable row shows a pointer cursor and a hover
highlight from the start — the affordance does not wait for a first selection.

A table with no `onRowSelected` has neither. Do not add a hover highlight to a read-only table as
visual feedback: it announces a click that leads nowhere.

Clicking anywhere in a row selects it, **except** on an interactive control inside a cell. A
button, link, input, checkbox or label in a cell keeps its own click. The same holds for the
keyboard: Enter or Space on a focused control activates that control, not the row.

This matters beyond the stray selection: selecting a row re-renders it, which remounts its cells
and closes anything the control had just opened.

## Responsive columns

Give a column a `dropAt` breakpoint and it hides once the table is narrower than that. Columns
without one always stay. Below, Age drops at 550px and Last Name at 700px; First Name and

### A long header ellipsizes rather than widening its column

A header must never be the reason a column is wider than its cells, so a label too long for its
column is truncated instead of widening it. "Replication Health" above sits on the narrowest track
in the table — narrow the frame and it cuts off.

Which width that happens at is not a fixed number: a column's width comes from its grow factor, so
dropping a neighbour hands its space to the columns that remain. A header can therefore truncate,
then read in full again at a narrower frame.

A truncated string header shows its full text in a tooltip on hover, so nothing is lost. The
tooltip appears only while the label is actually cut off — a tooltip repeating a header that reads
fine is noise. Headers built from a node rather than a string get none, since there is no text to
show: give those their own affordance if the label can be lost.

### Recovering the dropped values

Add `revealDroppedColumns` and each row gains a trailing `+N` trigger. Clicking it opens a popover
listing the dropped columns and their values for that row, so nothing is lost at a narrow width.

The trigger is a control inside a cell, so clicking it does not select the row — which is what
keeps the popover open.

### A control that cannot shrink will overflow its column

A column's width comes from its grow factor, and header and body cells shrink by the same rules,
so a column can end up narrower than the control inside it. A text button will not shrink below
its label, and it will overflow rather than clip.

Give such a button `iconOnly={n}` so it collapses to its icon below `n` px instead. Prefer that to
widening the column, which would cost every other column its share of the space.
