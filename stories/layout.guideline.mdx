### Context bar

The context bar is mostly there to carry the breadcrumb, when the page needs one. It can also hold a global refresh control.

## Resource listing pages

A resource listing page presents a collection of items of the same type.

There are 2 types: the full page versus the list-detail page (in this case, when the attributes of the resources needs to be explored a bit, or are numerous)

### Type

#### Full page

**What it is**<br />
A single list occupying the whole content area.

**When to use it**<br />
Items are consulted in place and do not need a side-by-side detail view. It is also used when the collection is known to hold only one or two items. The table then looks nearly empty, and that is accepted: there is no pattern for presenting a small fixed number of resources.

**Composition rules**

- The overall summary is always present.
  - It carries the resource icon as a Hero icon, the page title (often the resources name)
  - Other information could be in the summary, on the other side (full right), like specific configuration (activation of a feature, download a top level config, etc.)
- The main content holds the table and nothing else. The table owns the full area.
- When the resources are "browseable", then the item count is put as a `TextBadge` next to the title. The same when the table used in the main content doesn't have the search + result (that provides the count)

#### List-detail page

**What it is**<br />
A list on the left, the detail of the selected item on the right.

**When to use it**<br />
Items are compared and edited without leaving the list.

**When not to use it**<br />
When both sides are dense: the list needs several columns to be scanned, and the detail does not fit a key-value list. Use a full page for the collection and a dedicated page for the item. Editing then happens on the value itself (via an "Edit" button, for instance) or as a full page form.

**Composition rules**

- Selection drives the right panel. The selected row stays highlighted in the list.

- Actions on the selected item sit at the top of the detail panel, not in the list.

- The overall summary is present only when the collection is browsable, see below. When it is not, the detail panel carries its own header naming the selected item.

The split follows the information density on each side, measured on two things:

1/ how many columns the list needs to identify and compare an item,
2/ and whether the detail part is a single key-value list, or also carries tabs, nested tables, charts, configuration, forms.

- **30 / 70** when the list only identifies items (a name, possibly with a status) and the detail is where the work happens: tabs, several sections, nested tables, configuration.

- **65 / 35** when the list is the subject, scanned, sorted and compared over three or more columns, and the detail can be compacted in a key-value list. Key-value content is kept narrow on purpose (even if the values can be edited via forms or something else).

- **50 / 50** when both sides carry a moderate amount. Most often needed when you have two tables, one for the list, one for an attribute of an item in the list.

### Browsable collections

A collection is browsable when an item can be opened to reveal what it contains, so the page has several levels.

Browsability governs three things, that are tied:

- the context bar carries a breadcrumb;
- the overall summary is present, whichever form the page takes;
- the header states the level currently being viewed, and changes as the user goes deeper.

If not on the higher level, the overall summary also carries a control that moves up one level. It moves up the hierarchy, it does not go back in history.

When a collection has a single level, these 3 rules don't apply.

## Dashboards

A dashboard answers a specific question about a specific system. 

Its composition is deliberately not standardised: the blocks, their number and their arrangement follow the question being answered.

This is the only page type here without a canonical composition. 

Everything else still applies: same layout container, same header rules, charts follow the Chart guideline, and no block introduces a local component when one exists in the library.

## Forms

Form pages guidelines are to be defined. Until it is, follow the Form guideline for the component itself, plus the Modal guideline when the form is presented in a modal.
